# RMSKeyAlarm

楽天RMSライセンスキーの有効期限が残り指定日数（デフォルト5日前・1日前）になったら、Slackの指定チャンネルへ Incoming Webhook で通知するCronスクリプトです。**GitHub Actionsのスケジュール実行**で運用しています（PCの電源状態に依存せず、無料枠内で1日3回自動実行されます）。通信エラーなどの技術的な失敗はSlackへ通知せず、再試行・縮退運転・通知の拾い直しで自力回復します（「エラーを通知せず、自己修復する」を参照）。

`zidou` リポジトリ（`運用ツール/check_setup.py` の `_api_rakuten()`、`dashboard/health.py` の `_check_rakuten()`）で実際に使われている楽天RMS License Management APIの仕様に合わせて実装しています。

## 使っているAPI

```
GET https://api.rms.rakuten.co.jp/es/1.0/license-management/license-key/expiry-date?licenseKey={licenseKey}
Authorization: ESA {base64(serviceSecret:licenseKey)}
```

- 200: `{"expiryDate": "2026-09-01T23:59:59"}`
- 401: ライセンスキーが失効/認証情報が不正
- licenseKeyはクエリ必須（無いと400 DR0005）、GETのみ（POSTは405）

## 必要な認証情報

- `RMS_SERVICE_SECRET`（サービスシークレット、店舗単位で固定・**無期限**）
- ライセンスキー（約6ヶ月で失効）。取得元は下の2通りから選ぶ

## ライセンスキーはどこから取るか（2026-09-03 変更）

**なぜ変えたか（実際に起きた事故）**

2026-09-03、RMSでライセンスキーを再発行したのに、このアラームは
`:rotating_light: RMSライセンスキーが失効しています` を鳴らし続けた。原因は
コードではなく**キーの置き場所が4箇所に複製されていたこと**。

- `toiawase/.env` … 新キーに更新済み
- `RMSkeyAlarm/.env` / `hanbai/.env` / GitHub Secret の `RMS_LICENSE_KEY` … **旧キーのまま**

このAPIは「渡されたキー自身の期限」を返す仕様なので、旧キーを渡し続ける限り
毎日401（＝失効）になる。実測では旧キー `…2JRE` が HTTP 401、新キー `…mlpR` が
HTTP 200 / `expiryDate 2026-11-26` だった。**半年に1回しかない作業を4箇所に
手で反映する設計そのものが原因**なので、置き場を1つにした。

**方式A（推奨）: 共有DBから実行時に取る**

`SYNC_URL` と `SYNC_READ_TOKEN` を設定すると、実行のたびに共有DB
（Xserver の `sync.php`）から最新のキーを取ってくる。キーの入れ替えは
**更新画面（`key_update.php`）で1回貼るだけ**で、このリポジトリのSecretも
各PCの `.env` も触らなくてよくなる。

`SYNC_READ_TOKEN` は**読み取り専用トークン**（`config.php` の `read_tokens`）。
`rakuten_license_key` の照会しか通らず、`secret_get` 以外はサーバー側が403で弾く。
主トークンを入れないこと（入れると、このリポジトリのSecretが漏れたときに
送信履歴・顧客名・Yahoo!トークンまで読めてしまう）。

共有DBから取れなかったときは、`RMS_LICENSE_KEY` があればそれで判定だけは続ける
（**縮退運転**）。ただし**縮退運転中の401を「失効」と断定しない**。古いキーを
渡しただけかもしれないからで、ここを黙らせておかないと「共有DBが落ちている」を
「キーが失効した」と誤って通知して、上の事故をそのまま再現する。
200が返れば、そのキーの期限は本物なので通知してよい（どのキーで見たかは通知に書く）。
詳しくは下の「エラーを通知せず、自己修復する」を参照。

**方式B: 環境変数 `RMS_LICENSE_KEY`（従来どおり）**

`SYNC_URL` / `SYNC_READ_TOKEN` が未設定なら従来の動きになる。ローカルでの
動作確認と、共有DBへ登録するまでの移行期間用。再発行のたびに手で貼り替える
必要があり、貼り漏れると上の事故が再発する。

## GitHub Actionsでの運用（メイン）

`.github/workflows/check-license.yml` が1日3回（JST 9:00 / 12:00 / 16:00）自動実行します。回数を増やしてあるのは、通信で落ちた回を後の回が拾い直すため（同じ閾値の通知は1回しか出ません）。1回あたり数十秒なので、無料枠（プライベートリポジトリで月2,000分）に十分収まります。

### 初回セットアップ

1. GitHubのリポジトリページで **Settings → Secrets and variables → Actions** を開く
2. **「New repository secret」** で以下を1つずつ登録
   - `RMS_SERVICE_SECRET`（無期限。一度登録すれば触らない）
   - `SLACK_WEBHOOK_URL`
   - `SYNC_URL`（例: `https://kairu0505.xsrv.jp/toiawase/sync.php`）
   - `SYNC_READ_TOKEN`（読み取り専用トークン。**主トークンを入れない**）
3. `.github/workflows/check-license.yml` をリポジトリにpush（またはブラウザでアップロード）すれば、その日からスケジュール実行が有効になる

`SYNC_URL` / `SYNC_READ_TOKEN` を登録すれば、**キー再発行のときにGitHub側を触る必要は
なくなる**（更新画面で貼るだけ）。共有DBの用意が済むまでは、従来どおり
`RMS_LICENSE_KEY` を登録しておけば動く（両方あると共有DBが優先される）。
`RMS_LICENSE_KEY` のSecretは**残しておくことを勧める**。共有DBが不通の日に、そのキーで期限の見張りだけを続ける（縮退運転）ために使う。消しても動くが、その日は判定ごと止まる。

### 動作確認・運用

- 今すぐ実行して確認したい場合: リポジトリの **Actions** タブ → 左メニュー **「RMS License Key Alarm」** → 右側の **「Run workflow」** ボタンで手動実行できる
- 実行ログは同じActionsタブの各実行から確認できる
- スケジュールを変更したい場合は `check-license.yml` の3本の `cron:` を編集（UTC基準。JST = UTC+9）。減らしても通知は失われないが、通信障害から立ち直る機会は減る
- 通知条件（`WARNING_DAYS`等）を変えたい場合は同ファイルの `env:` を編集

## Renderへのデプロイ（Cron Job・任意）

このリポジトリには `render.yaml` を同梱しているので、Render の Blueprint 機能でそのままデプロイできます。

1. このディレクトリをGitリポジトリとしてpush（GitHub/GitLab）
2. Renderダッシュボードで「New +」→「Blueprint」を選び、このリポジトリを指定
3. `render.yaml` の内容に従って Cron Job (`rms-key-alarm`) が作成される
4. `sync: false` になっている環境変数（`RMS_SERVICE_SECRET`, `RMS_LICENSE_KEY`, `SLACK_WEBHOOK_URL`）をRenderの画面上で入力
5. スケジュールはデフォルトで毎日 UTC 0:00（JST 9:00）。変更する場合は `render.yaml` の `schedule` を編集（cron形式）
6. **`ALERT_MODE=exact` を設定すること。** Render の Cron Job はファイルが実行ごとに消えるため、`catchup` が使う通知済みの記録（`state/notified.json`）が残らない。そのままだと閾値を割っている間、毎回通知してしまう

Blueprintを使わず手動でCron Jobを作る場合は、Render上で以下を設定してください。

- Build Command: `npm install`
- Start Command: `npm start`
- Schedule: `0 0 * * *`（毎日 JST 9:00 相当）
- 環境変数: `.env.example` を参照して同名のキーを設定

## 通知条件

**Slackへ送るのは「結論」だけです。** 期限が近い／失効した、の2つ。
通信エラーなどの技術的な失敗は既定では送りません（`NOTIFY_ON_ERROR=false`）。

- `WARNING_DAYS`（デフォルト `5,1` = 5日前と1日前）で指定した残り日数を**割り込んだら**通知。カンマ区切りで何個でも指定可（例: `WARNING_DAYS=14,5,1`）
- `ALERT_MODE=catchup`（デフォルト）は**閾値ごとに1回だけ**通知します。5日前の実行が全部こけても、翌日の実行が「残り4日（5日前ぶん未送）」として拾い直します。1日に何回実行しても同じ閾値は二度送りません（どこまで送ったかを `state/notified.json` に記録）
- `ALERT_MODE=exact` は従来動作（残り日数がピッタリ一致した日だけ）。その日に実行できないとその閾値の通知は**永久に失われます**
- `ALERT_MODE=at_or_below` は閾値を割っている間ずっと毎日通知（スパムになりやすい）
- ライセンスキーが既に失効している場合（HTTP 401）は、`WARNING_DAYS`の設定に関わらず即座に通知します
- 技術的な失敗もSlackで見たい場合だけ `NOTIFY_ON_ERROR=true` にします

## エラーを通知せず、自己修復する（2026-09-17 追加）

**何が起きたか**

2026-09-17、GitHub Actions からの実行が
`:warning: RMSライセンスキーを取得できませんでした（期限の判定は行っていません）`
を出した。中身は通信エラー。同じ時刻に社内PCから同じURLを叩くと正常に応答した:

```
https://kairu0505.xsrv.jp/toiawase/sync.php        → HTTP 401 + JSON（0.55秒）
https://kairu0505.xsrv.jp/toiawase/secret_store.php → HTTP 403（.htaccess が効いている）
https://kairu0505.xsrv.jp/toiawase/key_update.php   → HTTP 200
```

つまりサーバーもキーも無事で、**GitHub Actions からXserverへの経路がその回だけ
届かなかった**だけ。キーは失効していない。

**方針: エラーは人に投げず、自分で直す**

このアラームは無人実行なので、**1回の失敗がそのまま人への通知になる**のが問題
だった。しかも通知を受け取った人に打つ手はない（数分後には直っている）。
そこで「技術的な失敗はSlackへ出さない」かわりに、**自力で回復する層を4つ**入れた。
Slackへ行くのは結論（期限が近い／失効した）だけになる。

**1. その場で粘る（再試行）** — `src/retry.js`

- 共有DBの取得は4回まで（5秒 → 15秒 → 30秒。合計約50秒）。楽天APIとSlackは3回まで
- **粘るのは「時間をおけば直る種類」だけ**: 通信エラー・タイムアウト・5xx・429
- **粘らないもの**: 401/403（トークン違い）、400、「共有DBに未登録」、
  そして**楽天APIの401（＝本当の失効）**。何度叩いても同じ答えなので、
  待つと通知が遅れるだけになる
- 楽天APIとSlackにもタイムアウトを入れた（従来は無制限で、応答が返らないと
  ジョブが固まる可能性があった）

**2. それでもダメなら縮退運転** — `src/keySource.js`

共有DBから取れなくても、`RMS_LICENSE_KEY`（Secret／`.env`）があればそのキーで
期限の判定だけは続ける。**見張りを止めない**ことを優先する。

- 200が返れば、そのキーの期限は本物なので通知してよい（どのキーで見たかは通知に明記）
- **401は「失効」と断定しない**。古いキーを渡しただけの可能性があるため、
  黙ってログに残し、共有DBが復旧してから判定し直す。
  これで 2026-09-03 の誤報（生きているキーを「失効」と鳴らし続けた）は再現しない

**3. その日のうちにもう一度やる（1日3回実行）** — ワークフロー

JST 9:00 / 12:00 / 16:00 の3回に増やした。9時の実行が通信で落ちても、12時が拾う。

**4. 取りこぼした通知は後から拾う（catchup）** — `src/notifyState.js`

「一致した日だけ通知」だと、その日に実行できなければ通知は永久に消える。
閾値を**割り込んだら**通知し、**どの閾値まで送ったかを記録する**方式に変えた。

- 5日前の実行が全部こけても、翌日「残り4日（5日前ぶん未送）」として届く
- 1日3回実行しても同じ閾値は二度送らない
- 記録するのは**Slackへ送れたあと**。送信に失敗した通知は「未送」のまま残り、次の実行が拾う
- 記録の中身は期限日と日数だけ（**キーは書かない**）。GitHub Actions では
  `actions/cache` で実行をまたいで持ち回る。消えても壊れない（最悪、通知が1回重複するだけ）

**気づく経路（Slackを鳴らさないかわりに）**

失敗した実行は終了コード1で終わるので、Actionsタブが赤くなり、GitHubから
ワークフロー失敗のメールが届く。技術的な失敗もSlackで見たいときは
`NOTIFY_ON_ERROR=true`。

**モックサーバーで確認した動作**（本番のSlack・楽天API・共有DBには触れていない）

| 状況 | 結果 |
| --- | --- |
| 共有DBが2回503 → 3回目成功 | 通知なしで正常終了（誤報が消える） |
| 共有DBのポートが閉じている（今回と同じ状況） | 50秒粘ったあと環境変数のキーで縮退、**期限通知は出る／エラー通知は0件** |
| 縮退運転中に楽天が401 | **何も通知しない**（失効と断定しない）。exit 1 |
| 共有DBも環境変数のキーも無い | **何も通知しない**。exit 1 |
| 共有DBのキーで401（本当の失効） | 即「失効しています」通知（`NOTIFY_ON_ERROR=false` でも出る） |
| 残り5日・初回 | 通知1件、`{"2026-09-22":[5]}` を記録 |
| 同じ日に2回目・3回目の実行 | 通知0件（重複しない） |
| 5日前を逃して残り4日 | 通知1件＋「5日前の通知を出せていなかったため、いま出しています」 |
| Slackが2回503 | 3回目で届く（通知を落とさない） |

  「ライセンスキーの取得元: 共有DB」と出ているかを確認すること

## 注意

`RMS_SERVICE_SECRET` は楽天RMSの認証情報そのものです。他リポジトリやログに平文で
残さないよう注意してください（このリポジトリの `.env` はGit管理対象外です）。

ライセンスキーは共有DBから取る方式にした場合、このリポジトリにはキー自体を
置きません。代わりに置く `SYNC_READ_TOKEN` は**照会1本に絞った読み取り専用**の
トークンにしてください。主トークンを置くと、露出したときの被害が
「楽天キーが読める」から「送信履歴・顧客名・Yahoo!トークンまで読める」に広がります。
